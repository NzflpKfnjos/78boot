# 无 UI 的最小 Android root 脚本控制方案

## 项目目标

在本项目中开发一个尽可能简单的 Android root 控制方案：不需要图形化管理器，通过命令行启动指定脚本，并使脚本及其子进程获得运行所需的 root 权限。

目标脚本的本地主机路径：

```text
/Users/a77/Desktop/git/tomato/release/1_no_login.sh
```

参考上游：

- KernelSU：https://github.com/tiann/KernelSU
- KernelSU-Next：https://github.com/KernelSU-Next/KernelSU-Next

本文件是开发计划，不代表已实现或已在设备上验证。当前尚未获取、审查两个上游的源码，也未确定目标设备或内核版本。上游选择应在兼容性验证后确定。

## 核心原则

1. 尽量复用成熟的内核 root 实现，避免第一阶段自行重写权限提升机制。
2. 无管理器 UI；通过 CLI 完成安装、启动、查看状态和回滚。
3. 首版只围绕指定脚本及参数 `1`、`2` 实现，不引入模块市场、多用户管理或复杂策略语言。
4. 以脚本的实际运行结果定义权限是否满足需求。`uid=0`、capabilities、SELinux 和挂载命名空间分别验证。
5. 保留可恢复的 boot 镜像和 userspace 安装版本，分别验证内核恢复与脚本入口回滚。

## 已确认的脚本行为

根据脚本的 shell 头部，可以确认：

- 使用 `/system/bin/sh`，启用 `set -eu`，要求 `id -u` 为 `0`。
- 在 `/data/local/tmp` 创建私有临时目录，设置 `umask 077`，退出时清理目录。
- 从脚本内嵌压缩包提取 `payload.elf` 和 `config_fetch_helper.elf`。
- 校验两个 ELF 的 SHA-256，随后设置执行权限。
- 要求 `/data/adb` 存在，使用相对路径向主程序传递 helper 位置。
- 接受一个参数 `1` 或 `2`；不传参数时进行交互式选择。
- 使用 FIFO 和 `awk` 过滤部分程序输出，等待子进程结束并返回其退出码。
- 依赖 `mktemp`、`tail`、`gzip`、`tar`、`sha256sum`、`cp`、`chmod`、`mkfifo`、`awk`、`nohup` 等命令。

尚未确认 ELF 的架构、动态链接依赖、具体系统调用、网络行为或所需 SELinux 权限，不能仅由 shell 头部推断这些能力。

脚本提示用户在悬浮窗中完成初始化。因此，“root 控制无 UI”不等于“目标程序完全无 UI”。传入 `1` 或 `2` 可以消除 shell 的选择提示；程序本身能否无人值守执行仍需设备验证。

## 拟议架构

```text
兼容目标设备的 KernelSU 或 KernelSU-Next
                |
       必要的 userspace 组件
                |
       root-control 命令行入口
                |
      校验路径、文件哈希和参数
                |
     sh <设备脚本路径> <1 或 2>
                |
       payload.elf / helper
```

首版优先保留上游必要的 userspace 组件。能否取消 Manager 安装、如何建立首次授权、如何为调用入口授予 root，必须通过所选上游源码和设备实验确认。不能假设删除 Manager 后任意普通进程就能自动获得 root。

`root-control` 本身不提供权限提升能力。它必须由已获得 root 的启动服务调用，或通过经验证的上游授权入口运行。第一版优先采用已有 root 启动上下文；若需要普通 shell 手动触发，再确定授权与请求通道。

拟议设备目录：

```text
/data/adb/root-control/
├── bin/root-control
├── config/root-control.conf
├── scripts/1_no_login.sh
├── hashes.sha256
├── logs/
└── state/
```

设备路径和主机路径不同。部署时将主机上的完整脚本复制到设备目录，不改动其内嵌 payload 的偏移和字节。

## 开发阶段

### 阶段 0：确定设备与源码基线

收集 Android 版本、设备型号、CPU ABI、内核版本与配置、boot/init_boot 布局、bootloader 状态，以及是否能构建和恢复镜像。确认脚本使用模式 `1` 还是 `2`，以及手动启动或开机启动需求。

获取两个上游，记录 commit 和许可证，比较目标内核支持、集成方式、userspace 依赖与无 Manager 授权路径。依据这些结果选择一个上游作为首版基线，不同时维护两套内核实现。

交付：设备信息、上游选择依据、固定 commit、构建方式与恢复步骤。

### 阶段 1：验证上游 root 与原始脚本

先建立可启动的上游基线，确认 root 上下文中的 UID、capabilities、SELinux domain 和挂载环境。在同一设备分别执行原始脚本的两个模式，保存输入、退出码、标准输出与标准错误。

检查 ELF 的 ABI、解释器和共享库依赖；区分 root 权限失败、动态链接失败、环境检测失败与程序自身初始化失败。

交付：可复现的基线记录和实际所需权限。取得 root 不代表目标脚本已经可正常运行。

### 阶段 2：实现最小无 UI 执行入口

实现 `root-control check`、`root-control run 1`、`root-control run 2`、`root-control status` 和 `root-control logs`。

入口检查 root 身份、固定脚本路径、脚本哈希、参数和必要目录。安装目录、配置、脚本和哈希记录均由 root 持有，普通用户不可写。哈希校验用于验证完整性；授权由调用身份和启动上下文决定。

保持完整脚本不变，使用系统 shell 执行，保留退出码。首版采用同步运行并记录状态；重复执行策略根据基线观察确定，必要时添加单实例锁。

交付：无 Manager UI 的可执行路径及其授权说明。先证明上游可支持该路径，再移除确实不需要的组件。

### 阶段 3：按实际错误补齐权限

先保持 SELinux enforcing，结合 AVC 日志定位阻止脚本运行的操作。仅为验证必需的访问添加 policy 或调整执行上下文；根据实际调用确认 capabilities 和挂载命名空间要求。

全局 permissive 不作为默认启动动作。任何扩大权限的变更都要有对应失败记录和修复后的对照结果。

交付：权限变更及证据，或者无需额外 policy 的验证结论。

### 阶段 4：按需加入开机启动

只有手动运行通过且程序满足无人值守条件后，才启用开机模式。通过所选上游支持的启动机制，在 `/data` 可用后执行，添加超时、日志和重复执行保护，避免阻塞系统启动。

是否使用 `/data/adb/service.d` 及其执行时机，以固定上游版本的实现为准。不要在未验证前把长时间运行的程序加入早期启动流程。

交付：可关闭的自动启动配置、启动日志与故障恢复结果。

### 阶段 5：安装、升级与回滚

提供安装、卸载和升级脚本。更新时先校验完整文件，再切换到新版本，并保存上一可用版本。记录版本、哈希和执行状态。

userspace 回滚恢复执行入口、脚本和配置；内核或镜像恢复使用独立的原始镜像与设备恢复流程。卸载时明确处理日志和状态目录。

交付：安装包、升级步骤、userspace 回滚脚本和设备镜像恢复说明。

## 验收标准

在同一设备、相同参数和相同环境中记录以下三组行为：

1. BASELINE：通过已验证的 root 上下文运行原始脚本。
2. MODIFIED：通过无 UI 的 `root-control` 运行同一脚本。
3. ROLLBACK：恢复上一版本后，再以相同输入运行。

每组记录命令、输入、UID、SELinux 状态、标准输出、标准错误、退出码与文件哈希。目标程序的可见行为和退出状态必须有设备证据。

额外验证：

- 参数 `1`、`2` 均能按基线执行；其他参数明确拒绝。
- 普通用户无法直接修改执行入口、配置、脚本或哈希记录。
- 非授权调用不能获得 root。
- 脚本被修改一个字节后完整性检查失败。
- 缺少脚本、依赖或必要目录时给出明确错误。
- 子进程退出码被正确传递，临时文件按脚本约定清理。
- 启用开机模式时，执行失败不会持续阻塞开机，并能关闭该模式。
- userspace 回滚后哈希与上一版本一致；内核恢复流程能够恢复原始镜像。

目标脚本包含二进制尾部。完整性测试应在副本上进行，不对原始脚本重新格式化或修改行数。

## 首版范围与下一步

首版交付一个上游基线、必要 userspace 组件、固定脚本执行入口、完整性校验、状态与日志、安装和回滚工具。开机启动以脚本实际支持无人值守为前提。

第一项执行任务是收集目标设备信息并获取上游源码，确认“无 Manager 的 root 启动上下文”是否可用。随后建立原始脚本基线，再开发执行入口。当前尚未开始内核构建、刷机或目标脚本执行。
